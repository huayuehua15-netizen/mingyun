# 11 · Go 工程规范与上手路线

这份文档写给"从来没用过 Go"的人。目标不是把你教成 Go 专家，而是让你在四周内能独立写这个项目的引擎层，并且写出来的东西不像"Java 程序员写的 Go"。

## 1. 先换脑子：Go 的四个价值观

| Java / Python 习惯 | Go 的做法 | 为什么 |
|---|---|---|
| 继承、抽象基类、层层封装 | 组合 + 小接口 | Go 没有继承，接口是隐式的（只要方法集匹配就自动实现） |
| 异常向上抛，最外层统一捕获 | 错误是返回值，逐层判断、逐层加语境 | 显式优于隐式；编译器会逼你处理 |
| 万物皆对象，方法挂在类上 | 方法是挂在类型上的普通函数，接收者可选值或指针 | 简单、无隐式 this |
| 多线程 + 锁 | goroutine + channel + context | 并发是一等公民，但代价是必须管生命周期 |

一句话总结：**Go 把"简单"当成硬指标。** 看到某个设计需要三层泛型加两个设计模式才能说清，那它在 Go 里就是错的设计。

## 2. 四周上手计划

每周都有可运行的产出，不要只看不写。

### 第 1 周：语法与类型（产出：干支计算 CLI）

学：变量与短声明、基本类型、slice/map、struct、方法、指针、流程控制、函数多返回值、包与导入。

练：

1. 写一个程序，输入 `2026-11-25`，输出"丙午年 己亥月 乙酉日"。先不查农历库，用儒略日 + 干支偏移自己算（这一步能让你真正懂 `time.Time` 与整数运算）。
2. 把上面改成 `go test` 能测的形式：把计算抽成包级函数，写表驱动测试跑 60 天，验证干支循环闭合。

关键认知：`slice` 是"指针 + 长度 + 容量"的三元组，函数传参传的是这个结构体的副本，所以 `append` 可能返回新底层数组——这是新手第一大坑。

### 第 2 周：错误、接口与测试（产出：CSV 转 JSON 工具）

学：`error` 接口、`errors.Is/As`、`fmt.Errorf` 的 `%w`、自定义错误、接口定义与断言、`encoding/json`、文件读写、`testing` 包。

练：

1. 读一个 CSV（列：日期、时辰、性别），逐行转成 JSON 数组输出。坏行要报出"第几行、哪个字段、为什么错"，不能只报 "invalid input"。
2. 定义 `type Validator interface { Validate() error }`，让不同输入类型各自实现。
3. 用 `httptest` 写一个 handler 的测试（此时还没学 Web，先只测函数）。

关键认知：**错误信息是给人看的**。`return err` 三次以上，排查时你会骂自己。

### 第 3 周：并发与 HTTP（产出：SSE 回显服务）

学：goroutine、channel、`select`、`context`、`sync`、`net/http`、`http.Flusher`。

练：

1. 写一个服务：`GET /stream` 每秒推一条 `data: tick`，客户端断开时服务端要能感知并退出（用 `r.Context().Done()`）。
2. 用 `go test -race` 跑一个"1000 个 goroutine 同时写同一个计数器"的反例，亲眼看到 race 报告长什么样；再用 `atomic` 或 mutex 修好。
3. 故意写一个 goroutine 泄漏（channel 无人读、无 context 退出），用 `runtime.NumGoroutine()` 观察数量只增不减。

关键认知：**每个 goroutine 都必须有明确的退出路径**。写 `go func()` 之前先回答"谁让它结束"。

### 第 4 周：数据库与工程化（产出：迷你 CRUD + Docker）

学：`pgx`、`sqlc`、`goose`、`log/slog`、`caarlos0/env`、多阶段 Dockerfile、`go work`。

练：

1. 建一张表，用 sqlc 生成查询，写 GET/POST 两个接口。
2. 打成 distroless 镜像，跑起来，验证 `time.LoadLocation("Asia/Shanghai")` 不 panic（这一步能让你记住 `time/tzdata`）。
3. 用 `go work` 把两个 module 串起来（正是本项目 `paipan` 与 api 的关系）。

四周后，你已经具备写 M1 里程碑的全部技能。剩下的都是业务知识。

## 3. 五个必须真正理解的概念

### 3.1 接口是隐式实现的

只要类型有对应方法，就自动满足接口，不需要 `implements` 声明。所以：

- **接口定义在使用方**（消费者需要什么就定义什么），不在实现方。
- **接口越小越好**，1–2 个方法最佳。本项目的 `Diviner` 有 4 个方法，已经偏大，不要再加。

### 3.2 error 是值，不是异常

| 做法 | 是否正确 |
|---|---|
| `if err != nil { return err }` 连做三层 | 不推荐，丢失上下文 |
| `return fmt.Errorf("cast liuyao: %w", err)` | 推荐 |
| `errors.Is(err, ErrOutOfRange)` 判类型 | 推荐，用哨兵错误 |
| `err.Error() == "not found"` 判类型 | 禁止，字符串会变 |
| `panic` 处理业务错误 | 禁止，panic 只用于"程序不可能继续"的场景 |

### 3.3 context 是生命周期的传递

- 第一个参数，名字必须叫 `ctx`。
- 不许存进 struct 字段。
- 所有可能阻塞的调用（DB、HTTP、channel 接收）都要带上它。
- `context.WithTimeout` 用于单次调用；`context.WithCancel` 用于"用户关页面了"。
- **不要**用 `http.Client.Timeout` 控制流式请求的总时长——它会连正在读取的流一起掐断。用 context。

### 3.4 defer 是栈式的，且在函数返回时执行

- `defer resp.Body.Close()` 必须在 `err` 检查之后立刻写，别忘。
- 循环里 `defer` 会累积到函数结束才执行——循环里要显式关闭，或包一层匿名函数。
- `defer` 有微小开销，但正确性远比这点开销重要。

### 3.5 值语义与指针

- 小结构体（< 几个字段）传值；大结构体或需要修改时传指针。
- 方法接收者：读操作可用值接收者，写操作必须指针；**同一类型的所有方法接收者风格要统一**。
- map 和 slice 本身是引用语义的"描述符"，传值时改元素会影响原对象，但 `append` 可能不。

## 4. 目录规范

Go 社区共识 + 本项目落地：

| 目录 | 用途 | 本项目 |
|---|---|---|
| `cmd/` | 可执行入口，每个子目录一个 main | `cmd/mingyun/main.go` |
| `internal/` | 私有包，外部无法 import | `internal/handler`、`internal/service` 等 |
| `pkg/` | **不要用** | 本项目的公开库是独立 module `paipan/` |
| `api/` | OpenAPI 定义 | `api/openapi.yaml` |
| `migrations/` | 迁移 | goose SQL |
| `deploy/` | 部署物 | compose、nginx |

命名规则：包名小写、单词连写不用下划线（`paipan` 而非 `pai_pan`）；避免 `util`、`common`、`helpers` 这类无意义包名；文件名用蛇形（`true_solar_time.go`）。

**禁止 `init()` 做初始化**。依赖注入在 `main` 里显式装配，看得见的东西才好排查。

## 5. 错误处理规范（写进 CONTRIBUTING）

1. 包装必须带动作：`fmt.Errorf("load chart %s: %w", id, err)`。
2. 业务错误用哨兵值：`var ErrChartNotFound = errors.New("chart not found")`。
3. 面向用户的错误单独一层：内部错误记日志，对外只返回错误码 + 人话，不泄露 SQL 与堆栈。
4. 不吞错：`_ = doSomething()` 只允许在明确无害处（如关闭已关闭的连接），且要写注释。
5. 错误只处理一次：要么记录日志并返回，要么包装并上抛，不要两者都做。

## 6. 并发规范与雷区

| 雷区 | 症状 | 正确做法 |
|---|---|---|
| goroutine 无退出路径 | 内存缓慢上涨，最终 OOM | `select { case <-ctx.Done(): return; case <-ch: }` |
| 从接收方 close channel | panic: send on closed channel | 只有发送方关闭；或干脆不关，靠 context 退出 |
| 循环变量捕获 | Go 1.22 前的经典 bug | Go 1.22 起每次迭代独立变量，此坑已消除；但仍别在闭包里持有大对象 |
| 共享 map 并发写 | fatal error: concurrent map writes | `sync.RWMutex` 或 `sync.Map`（仅在读多写少且键独立时） |
| 忘记 `defer mu.Unlock()` | 死锁 | 加锁后立刻 `defer` |
| 在持有锁时做 IO | 吞吐骤降 | 锁内只做内存操作 |
| `wg.Add` 在 goroutine 里 | panic / 计数错乱 | `wg.Add` 必须在启动前 |
| SSE handler 不读 context | 僵尸连接堆积 | `c.Stream` 内部循环检查 `c.Request.Context().Err()` |

Go 1.25 起 `sync.WaitGroup` 有 `Go(f)` 方法，可以直接 `wg.Go(func(){...})`，省掉 `Add/Done` 配对出错的可能——本项目优先用它。

**并发量的量级判断**：本项目绝大部分请求是"一次计算 + 一次网络等待"，根本不需要 worker pool。不要为了"显得专业"引入 `ants` 之类的池——先量，再优化。

## 7. 时间、JSON、数值的坑（本项目高发区）

| 坑 | 说明 | 解法 |
|---|---|---|
| 容器里没有时区数据库 | distroless 无 `/usr/share/zoneinfo`，`LoadLocation` 报错 | 二进制 `import _ "time/tzdata"` |
| `time.Now()` 直接入库 | 服务器时区不同，数据错乱 | 统一 `time.Now().UTC()` 存，展示时转 |
| `time.Time` JSON 序列化 | 默认 RFC3339，带时区偏移，格式不符前端预期 | 自定义 `MarshalJSON` 或统一在前端解析 |
| 用 float 算钱 | 精度丢失 | `shopspring/decimal` 或整数分 |
| `nil` slice 序列化成 `null` | 前端拿到 null 而非 `[]` | 初始化时给空切片 |
| map 遍历顺序随机 | 输出不稳定，快照测试挂 | 需要有序就排序键 |
| 结构体字段没 tag | JSON 出 `FieldName` 而非 `snake_case` | 每个对外结构体都写 tag |
| `omitempty` 吞掉零值 | 数字 0 被删掉，前端缺字段 | 该保留的别加 `omitempty` |

**快照测试的前提是序列化稳定**：`encoding/json` 的 map 键排序是确定的（Go 1.12 起），但 slice 顺序取决于你的构造逻辑，构造逻辑必须确定。

## 8. 测试规范

| 类型 | 写法 | 本项目用在哪 |
|---|---|---|
| 表驱动单测 | `cases := []struct{name string; in X; want Y}` + `t.Run(c.name, ...)` | 每条术数规则 |
| 黄金文件 | 读 `tests/golden/xxx.json` 比对，`-update` 标志重生成 | 完整盘面 |
| 属性测试 | 循环不变量断言（干支 60 闭合、旬空自洽） | 历法层 |
| 接口测试 | `httptest.NewServer` + 真实 handler | API |
| 并发测试 | `go test -race ./...` | 全局 |
| 基准测试 | `testing.B`，只在有性能疑问时写 | 大六壬涉害计算 |

规则：测试文件与被测文件同包（`xxx_test.go`）；不引入 mock 框架，用手写假实现；覆盖率不追求数字，只要求"每条规则有对应用例"。

## 10. 依赖选择原则

1. **能用标准库就不引第三方**：`log/slog`、`net/http`、`encoding/json`、`testing` 都够用。
2. 引入一个依赖前，看三件事：最近半年是否发版、是否有测试、许可证是否 MIT/Apache/BSD。
3. 拒绝"全家桶"式框架（自带 ORM + 依赖注入 + 代码生成的）。
4. 依赖数量控制在 20 个直接依赖以内。每多一个，Docker 镜像和供应链风险都增加。

本项目的直接依赖预估：`gin`、`validator`、`pgx`、`goose`、`go-redis`、`asynq`、`jwt`、`x/crypto`、`caarlos0/env`、`uuid`、`decimal`、`lunar-go`、`testify`、`x/sync`、`x/time`。约 15 个，合理。

## 11. 从 Python / Java 带过来的坏习惯

| 坏习惯 | 为什么不行 | 改成 |
|---|---|---|
| 一个文件几千行 | 无法 review、无法复用 | 按职责拆文件，单文件 < 400 行 |
| 到处 `map[string]interface{}` | 类型不安全，运行时才炸 | 显式 struct |
| 用全局变量传配置 | 无法测试、并发不安全 | 依赖注入，`main` 装配 |
| try/except 式地包住一切 | Go 没有异常，包住也没用 | 逐层返回 error |
| 为每个实体写 Service/Impl/Factory | 过度设计 | 一个 struct + 一组方法 |
| 用 `panic` 处理业务错误 | 服务直接挂 | error |
| 深拷贝一切以防副作用 | 性能与心智负担 | 明确所有权，只读数据共享 |
| 用日志代替错误返回 | 调用方拿不到失败信号 | 返回 error，必要时再记日志 |

## 12. 本项目的实现顺序（照着做能少走弯路）

1. `cmd/mingyun/main.go` + 子命令骨架（serve / migrate / paipan / version）。
2. `paipan/calendar`：先写"干支 + 儒略日"纯算术，通过 60 日闭合测试。
3. 接入 `lunar-go` 取节气与农历，写交叉校验测试。
4. 写真太阳时（经度修正 + 均时差），用"广州 vs 北京同一时刻"的用例验证。
5. `paipan/schema`：定义 `Chart`、`Fact`、`CalendarContext`。
6. `paipan/liuyao`：先只支持"手动录入 6 爻"，把装卦跑通。
7. 加 64 卦静态数据（八宫归属、卦名、卦辞）——用一个 CSV 或 Go 字面量，别写在逻辑里。
8. 补摇卦映射（输入背数数组）。
9. 写 `BuildFacts`，用 CLI 输出看一眼，人工判断"这段话能不能让模型讲对"。
10. 再进 API 与前端。

**第 6 步是关键**：先不做动画、不做随机、不做 Web，只让"6 个输入 → 1 张正确的盘"。这一步跑通，后面全是加法。

## 14. 最后一条建议

学 Go 最快的路径不是看书，是**写一个必须跑起来的东西**。这个项目正好：它有明确的对错（排盘结果对不对）、有真实的复杂度（不是玩具 CRUD）、有可展示的产出（一个网站）。

从第 6 步那个"6 个输入 → 1 张盘"的小程序开始。它跑通的那天，你就算会 Go 了。
