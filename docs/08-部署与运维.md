# 08 · 部署与运维

## 1. 目标形态

一条 `docker compose up -d` 起全站，五个容器，一台 2 核 4G 的小机器能跑。这是产品的交付底线，任何"为了架构优雅而增加一个中间件"的提议都要先过这一关。

## 1.1 当前单机版（2026-11）

仓库当前先落地的是 **api + nginx 两个容器**的单机版，没有 Postgres / Redis / worker / migrate。盘面与模型配置用文件存储：

- 数据目录 `MINGYUN_DATA_DIR`，Docker 下为 `/data`；
- Compose 命名卷 `mingyun-data`；
- 盘面 `charts.json`，模型配置 `ai-settings.json`；
- 该方案的部署、备份与安全边界以 `12-模型中心与数据持久化.md` 为准。

目标形态里的 Postgres/Redis 与账号体系仍然有效，但尚未落地；不要把本节的五容器拓扑当成当前 `docker-compose.yml` 的实际内容。

## 2. 服务拓扑

| 服务 | 镜像 | 职责 | 端口 | 依赖 |
|---|---|---|---|---|
| nginx | `nginx:1.27-alpine` | 静态托管前端、反代 API、SSE 直通、gzip | 80 / 443 | api |
| api | `ghcr.io/<org>/mingyun:latest`，命令 `serve` | HTTP 接口、SSE、排盘 | 8080（内网） | postgres、redis |
| worker | 同一镜像，命令 `worker` | asynq 消费：分享图清理、报告生成、订阅到期 | — | postgres、redis |
| migrate | 同一镜像，命令 `migrate up` | 一次性迁移，跑完退出 | — | postgres |
| postgres | `postgres:16-alpine` | 主库 | 5432（不对外） | — |
| redis | `redis:7-alpine` | 缓存、额度、队列 | 6379（不对外） | — |
| ollama（可选 profile） | `ollama/ollama` | 本地模型推理 | 11434（内网） | — |

`api` 与 `worker` **用同一个镜像不同命令**，这是 Go 单二进制带来的直接收益：一次构建，两种角色，版本永不错位。

## 3. 镜像构建

多阶段：

| 阶段 | 基础镜像 | 动作 |
|---|---|---|
| builder | `golang:1.25-alpine` | 装 git/tzdata；`CGO_ENABLED=0 go build -trimpath -ldflags "-s -w"` |
| 前端 | `node:22-alpine` | pnpm install → pnpm build 出 `dist` |
| runtime | `alpine:3.21` | 装 `ca-certificates`，建非 root 用户（uid 10001），只 COPY 二进制 |

要点：

- `CGO_ENABLED=0` 是能上精简镜像的前提。本项目所有依赖（含 lunar-go）都是纯 Go，成立。
- 二进制里 `import _ "time/tzdata"`，否则没有 `/usr/share/zoneinfo` 的镜像里 `time.LoadLocation("Asia/Shanghai")` 会直接失败——这是新手最常见的一个上线事故。本项目已在 `cmd/mingyun` 内嵌。
- 运行时选 `alpine` 而不是 `gcr.io/distroless/static`：distroless 要从 gcr.io 拉取，国内构建经常超时；alpine 只多几 MB，且自带包管理便于装 CA 证书。二进制已静态编译，想换回 distroless 随时可换。
- 实测镜像 22.9MB（api 单容器），在 25–35MB 目标内。
- 前端 `dist` 单独 COPY 进 nginx 镜像，不塞进 Go 镜像。

国内构建加速：`GOPROXY=https://goproxy.cn,direct`，`npm_config_registry=https://registry.npmmirror.com`，在 Dockerfile 用 ARG 暴露，不强绑。若 `docker.io` 拉基础镜像超时，可先从镜像站拉再打本地 tag：

```
docker pull docker.m.daocloud.io/library/alpine:3.21
docker tag docker.m.daocloud.io/library/alpine:3.21 alpine:3.21
```

### 4.1 当前单机版实际变量

|---|---|---|

| `MINGYUN_DATA_DIR` | `data` | 数据目录；Compose 用 `/data` |
| `MINGYUN_MODEL_SETTINGS` | `on` | `off / false / 0 / readonly` 时网页设置只读 |

Dockerfile 已把 `/data` 建好、chown 给非 root 用户 `mingyun` 并 `chmod 700`；Compose 的 `mingyun-data` 卷挂到 `/data`。若要改成宿主机目录 bind mount，必须保证容器内 UID 10001 可写。

## 5. 首次启动流程

1. `cp .env.example .env`，填四项必填（APP_BASE_URL / APP_SECRET / JWT_SECRET / ENCRYPTION_KEY / DATABASE_URL 中的密码 + 模型三件套）。
2. `docker compose up -d postgres redis`，等健康。
3. `docker compose run --rm migrate`。
4. `docker compose run --rm api create-admin --email $ADMIN_EMAIL`（交互输入密码）。
5. `docker compose up -d`。
6. 访问 `http://localhost:8080`，用管理员登录，进后台配 provider（若 `LLM_DEFAULT_*` 已填可跳过）。

把这一串写进 `deploy/init.sh`，并在 README 首屏给出一段可直接复制的命令。

## 6. 反向代理要点

nginx 配置里三个必须项：

| 配置 | 值 | 原因 |
|---|---|---|
| SSE 路径 | `proxy_buffering off;` `proxy_cache off;` `X-Accel-Buffering: no` | 否则解读变成"等 20 秒一次性吐出" |
| 超时 | `proxy_read_timeout 300s;` | 长解读会超过默认 60s |
| 请求体 | `client_max_body_size 2m;` | 分享图上传；不要给 20m，没人传大文件 |

另需：`gzip on` 对 `text/css application/javascript application/json` 生效；静态资源 `Cache-Control: public, max-age=31536000, immutable`（文件名带 hash）；`index.html` 必须 `no-cache`。

HTTPS 交给用户自备（Certbot 或云厂商），仓库提供一份可选的 `deploy/nginx-tls.conf.example`，不内置自动签发脚本。

## 7. 数据与备份

| 数据 | 位置 | 备份策略 |
|---|---|---|
| PG | 命名卷 `pgdata` | 每日 `pg_dump -Fc` 到 `backups/`，保留 14 天；重要节点做一次 `pg_basebackup` |
| Redis | 命名卷 `redisdata` | 只存可重建数据，不做备份；AOF 关闭，RDB 保留 |
| 分享图 | 对象存储或卷 `uploads` | 随对象存储策略；本地卷则每周 rsync |
| 当前单机版 `mingyun-data` | Docker 命名卷 `/data` | `charts.json` + `ai-settings.json`；按密钥文件管理，备份不要公开 |
| 密钥 | `.env` | **不入库**，用户自行保管；丢失意味着 provider key 无法解密 |

`deploy/backup.sh` 提供：dump + gzip + 按日期命名 + 删除 14 天前。文档里明确写"恢复步骤"，不能只给备份不给恢复。

恢复：停 api/worker → `pg_restore -d mingyun --clean` → 起服务 → 校验 `/readyz`。

## 8. 升级与回滚

- 升级：`docker compose pull` → `docker compose run --rm migrate` → `docker compose up -d`。
- 回滚：镜像 tag 换回旧版本 + **数据库迁移必须是可回滚的**（见 04 的"只增不改"约束）。破坏性变更一律分两个版本发布，保证任一版本都能独立运行。
- 迁移失败时 `migrate` 容器退出码非 0，compose 的 `depends_on: condition: service_completed_successfully` 会阻止 api 启动——这是刻意的，宁可站点起不来，也不要带着半套 schema 对外服务。

## 9. 资源占用（实测预估）

| 服务 | 常驻内存 | CPU |
|---|---|---|
| api | 80–150MB | 空闲 < 1%，出盘峰值单核 30% |
| worker | 40–80MB | 低 |
| postgres | 150–300MB | 低 |
| redis | 30–60MB | 低 |
| nginx | 10MB | 低 |

2 核 4G 可支撑日均 3000 次排盘、500 次解读。瓶颈会先出现在模型 API 的并发限制上，而不是本机。

## 10. 常见故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 容器起不来，日志报 `unknown time zone` | distroless 缺 tzdata | 确认二进制 import 了 `time/tzdata` |
| `LoadLocation` panic | 同上 | 同上 |
| 解读不流式，一次性返回 | nginx 缓冲或反代（Cloudflare）缓冲 | 关 buffering；CF 需关闭 "Buffering" |
| 出盘报 500，日志 `invalid date` | 前端传了无时区时间 | 前端统一 `toISOString()`，后端强制要求 RFC3339 |
| 中文乱码 | DB 编码不是 UTF8 | 建库时 `ENCODING 'UTF8'`，compose 里设 `POSTGRES_INITDB_ARGS` |
| 额度数字不对 | 多副本下用了进程内限流 | 改 Redis Lua 原子操作 |
| 镜像 300MB+ | 没有 `-s -w` 或多阶段没做干净 | 检查 Dockerfile，runtime 阶段不应有 go 工具链 |
| 迁移卡住 | 长事务锁表 | 迁移里禁止 `ALTER TABLE ... SET NOT NULL` 直接加在千万行表上 |

## 11. CI / CD

GitHub Actions 三个 workflow：

| 文件 | 触发 | 内容 |
|---|---|---|
| `ci.yml` | PR / push main | `golangci-lint run`；`go test -race ./...`；`go vet`；前端 `typecheck + lint + test`；OpenAPI 契约校验 |
| `release.yml` | tag `v*` | buildx 构建 amd64/arm64；推 `ghcr.io`，tag 为版本号与 `latest`；生成 `checksums.txt`；创建 GitHub Release |
| `nightly.yml` | 每日 03:00 | 全量历法交叉校验（1900–2100 抽样）、黄金样本回归、依赖漏洞扫描（govulncheck） |

镜像同时推 `ghcr.io` 与可选的 Docker Hub。Release 说明里附 `docker-compose.yml` 的原始链接，方便用户直接下载而不 clone 整个仓库。
