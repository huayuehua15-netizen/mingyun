# 04 · 数据模型设计

## 1. 总体约定

| 约定 | 规则 |
|---|---|
| 主键 | `uuid`（UUIDv7，时间有序，避免 B-Tree 随机写入） |
| 时间 | 全部 `timestamptz`，入库前转 UTC；展示层按时区渲染 |
| 软删除 | 用户可见资源用 `deleted_at timestamptz`，查询一律带 `deleted_at IS NULL` |
| 命名 | 表名复数蛇形；列名蛇形；外键 `{表名单数}_id` |
| 枚举 | 用 `text` + CHECK 约束，不用 PG enum（改值要锁表） |
| 金额 | `numeric(12,4)`，单位元；Go 侧用 decimal，禁止 float |
| JSON | 只用于不可枚举的结构（盘面快照、facts、provider 参数） |
| 索引命名 | `idx_{表}_{列}`、`uq_{表}_{列}` |

## 2. 实体关系

用户（users）是强实体；游客（guest_devices）是弱实体，可升级为正式用户。一张盘（charts）属于用户或游客之一，**二者必居其一**。一张盘可派生多个会话（conversations），一个会话含多条消息（messages）。用量（usage_records）挂在消息上，便于按次核算成本。订单（orders）与订阅（subscriptions）属于用户。

### 3.3 charts（核心表）

| 列 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | uuid | PK | |
| user_id | uuid | FK users, NULL | 与 guest_device_id 互斥 |
| guest_device_id | uuid | FK guest_devices, NULL | |
| method | text | CHECK in ('liuyao','daliuren','ziwei') | |
| title | text | | 用户可改，默认自动生成（如"丙午年十月廿五 问求职"） |
| question | text | | 所问之事，≤ 200 字 |
| input | jsonb | NOT NULL | 归一化后的输入（出生信息脱敏后） |
| calendar | jsonb | NOT NULL | CalendarContext 全量 |
| school | jsonb | NOT NULL | 本次流派配置 |
| payload | jsonb | NOT NULL | 完整盘面 |
| facts | jsonb | NOT NULL | 扁平事实清单 |
| engine_version | text | NOT NULL | 如 liuyao@1.0.0 |
| calendar_version | text | NOT NULL | 历法层版本 |
| snapshot_hash | char(64) | NOT NULL | sha256(payload+school+版本) |
| entropy_record | jsonb | | 摇卦记录（非六爻为 NULL） |
| warnings | jsonb | | 边界提示 |
| created_at | timestamptz | NOT NULL | |
| deleted_at | timestamptz | | |

约束：`CHECK ((user_id IS NULL) <> (guest_device_id IS NULL))` —— 必须有且只有一个归属。

索引：
- `idx_charts_user_time`（user_id, created_at DESC）WHERE deleted_at IS NULL
- `idx_charts_guest_time`（guest_device_id, created_at DESC）
- `idx_charts_method`（method）
- `idx_charts_hash`（snapshot_hash）——用于解读缓存与去重

**分表预案**：charts 是增长最快的表。单表超过 2000 万行或单表体积超 50GB 时，按 `created_at` 做月度分区（PG 声明式分区），迁移不影响 API。

## 4. 快照与可复现

`charts` 表一次性写入 `payload + facts + school + engine_version + calendar_version + snapshot_hash`，此后**永不更新**（除 title / deleted_at）。

这样做的三个直接收益：

1. 解读永远基于当时的盘面，规则升级不会让老帖子的断语对不上盘。
2. 同一 snapshot_hash 可全局去重，也能做解读缓存键。
3. 出现争议时可导出完整证据链：输入 → 版本 → 盘面 → 结论。

## 5. sqlc 与迁移

- 所有查询写在 `internal/repository/queries/*.sql`，`sqlc generate` 产出 `internal/repository/db/*.go`。
- 迁移用 goose，文件放 `migrations/`，通过 `embed.FS` 打进二进制，`mingyun migrate up` 执行。
- 迁移规范：**只增不改**。修改列类型必须"新建列 → 回填 → 双写 → 切读 → 删旧列"，分多个版本发布。禁止在迁移里写业务逻辑。
- 每个迁移文件必须有 `-- +goose Up` / `-- +goose Down`，Down 必须真的能回滚（CI 会跑一次 up→down→up）。

## 6. 数据保留与删除

| 数据 | 保留策略 |
|---|---|
| 盘面 | 用户主动删除后软删 30 天，之后物理删除 |
| 会话与消息 | 随盘一起删 |
| 用量记录 | 保留 24 个月（财务对账需要），不含正文 |
| 游客设备 | 90 天无活动物理删除 |
| 出生信息 | 只存 `charts.input` 中必要字段；用户可选"记住出生信息"，则加密存 `users.birth_profile_enc`，可一键清除 |
| 日志 | 30 天，正文不入日志（只记 ID 与长度） |

## 7. 容量估算（v1.0 单机）

| 表 | 单行估算 | 日增（按 1000 张盘） | 年增 |
|---|---|---|---|
| charts | 6–12 KB（payload + facts） | ~10 MB | ~3.5 GB |
| messages | 1–3 KB | ~5 MB | ~1.8 GB |
| usage_records | 200 B | ~0.2 MB | ~70 MB |

单机 PG 完全够用。真正占空间的是分享图，务必放对象存储或独立卷，不进数据库。
