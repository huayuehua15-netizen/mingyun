# 10 · 路线图与里程碑

## 1. 估算前提

这是一份"一个人、边学 Go 边写"的排期，不是团队排期。假设：每周可投入 15–20 小时；Go 从零开始；术数规则需要边查资料边实现。所有工期都是**日历周**，已含学习成本与返工，不含 UI 精修。

若按此排期推进，v1.0 大约 6 个月。想更快，只有一个办法：**砍术数，不砍质量**。

## 2. 里程碑

### M-1 · Go 上手（2 周）

| 交付 | 验收 |
|---|---|
| 一个能跑的 CLI 小项目（如"输入公历日期输出干支"） | 能独立编译、跑测试、看懂报错 |

## 4. 每个里程碑的"可停止点"

开源项目最怕做到一半没动力。设计三个可停止点，让任何阶段的成果都独立成立：

| 停止点 | 此时已有什么 | 可以怎么用 |
|---|---|---|
| S1（M1 末） | 一个准确的六爻排盘 CLI 与库 | 作为独立工具发布，先积累口碑 |
| S2（M2 末） | 可用的六爻网站 | 小范围内测，收反馈，验证交互 |
| S3（M4 末） | 六术齐全的排盘站 | 已足够开源，商业化可后补 |

## 5. 建议的开发顺序（避免返工）

1. **先写日历层，且先写测试。** 用已知答案倒推（如"2026 年立春是 2 月 4 日某时"），不要凭感觉调。
2. **六爻先做"手动录入"模式。** 跳过随机与动画，直接把 6 个阴阳动静变成完整盘面。这条路径最容易验证对错。
3. **再补随机摇卦。** 随机只是入口，不影响引擎正确性。
4. **最后做前端动效。** 动画是锦上添花，不能成为阻塞项。
5. **大六壬与紫微复用日历层**，不要各写一套。

## 6. v1.1 之后的候选

| 优先级 | 功能 | 理由 |
|---|---|---|
| 高 | 古籍 RAG | 直接提升解读可信度 |
| 高 | 分享图 + 短链 | 增长主要靠分享 |
| 中 | 奇门遁甲 | 用户呼声高，但规则复杂度最高，单独排期 |
| 中 | 流年运势长报告 | 付费点，但成本高、易越界 |
| 低 | 多语言 | 海外术数受众存在但分散 |
| 低 | 移动 App | Web 已够，App 增加审核与合规成本 |
